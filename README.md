# iPhone 18

一台 432 毫米长的手机的官网。《爱情公寓》里胡一菲举着它问「这爱疯18怎么用」，这个页面就是它的官方产品页。

**这是一个虚构的概念设计，与 Apple Inc. 无关。**

## 这是什么

不是一个普通的产品落地页，是一次仿冒。整个页面的目标是：在前三秒里让人以为这是苹果官网，然后才反应过来这台手机长得不对劲。所以视觉系统不做任何自由发挥，色值、字号、字距、按钮、法务区块全部照抄苹果在用的真实数值；笑点全部交给参数和不加修饰的渲染，文案一句玩笑都不开。`n`n页面没有全局导航栏：真实产品页顶部那条 48 px 的毛玻璃条会挡住首屏的产品，而这个页面的第一屏必须干净。

技术上是 Vite + TypeScript + three.js。一台程序化生成的手机，一支从头到尾不切镜的摄影机，滚动位置直接映射成镜头轨迹。

## 跑起来

```bash
npm install
npm run dev        # http://localhost:5273
npm run build      # 类型检查 + 生产构建
npm run typecheck
```

运行时依赖只有 `three` 和 `lenis`。`three-bvh-csg` 与 `three-mesh-bvh` 用来在启动时做一次布尔运算，把接口、扬声器孔和镜头凹腔真正从机身上挖出来。`three-bvh-csg` 锁在 `0.0.17`：`0.0.18` 要求 three >= 0.179，本项目在 0.171。

## 设计的主轴

**手机的 432 毫米，就是页面的长度。**

一个 6:1 的物体放进 16:9 的视口，只能是一根牙签。常规做法是缩小居中，那样整页都废了。这里的做法是永远不给看全貌，直到笑点该落地的那一刻：往下滚，就是沿着机身往下走。

## 几处不显然的决定

**几何全部程序化，不下载模型。** 机身是一个圆角矩形挤出体，1 个场景单位 = 1 毫米，所以几何参数、镜头framing 和页面上的标注线说的是同一套数字，改尺寸不用回 Blender，也没有任何外部资源会 404。

**ExtrudeGeometry 的 bevel 必须是正数。** 正号给出正确的 iPhone 截面（平面内缩 65.6 毫米，中段最宽 72 毫米）；负号会把它翻成一条面包。这个符号是实测出来的，不是猜的。

**摄影棚环境光是手写的，不是 three 的 RoomEnvironment。** metalness 为 1 时铝金属没有漫反射项，环境贴图就是机身颜色本身。RoomEnvironment 平均太暗，机身渲染出来是灰的，而参考图是近白。自建的光照里有一块很亮的天花板、两块不对称的侧板（负责边缘那道竖直高光）和一块故意压暗的地板（负责背面自上而下的渐变）。

**near/far 是按深度精度选的，不是按裁剪选的。** 最近的关键帧是 52 毫米的镜片微距，最远的是 2.3 米的规格页。near = 1 时深度缓冲分辨不出屏幕与机身之间零点几毫米的高差，屏幕会直接被机身盖住（`duo` 折页曾经整块消失）。

**折页背景、机身、文案是三层的。** 折页底色 z-index 0，canvas z-index 1，文案 z-index 2。所以 `.fold` 本身不能带 z-index，否则底色和文案会被困在同一层，文案会掉到 canvas 后面。深色折页尤其重要：`.fold--dark` 只改文字颜色，底色得靠 `.fold::before` 真正铺上黑。

**水平构图用 truck，不用 target.x。** truck 让摄影机和目标点一起沿摄影机右轴平移，主体在画面里左右移动但距离不变。挪 target.x 是更顺手的写法，但它同时改变了摄影机到主体的距离，会悄悄把构图改掉。

**`html` 上的 `scroll-behavior: smooth` 和 Lenis 会打架。** Lenis 每帧都在调 `scrollTo` 推进它自己的缓动；CSS 还开着平滑滚动时，每一次调用都会再起一段浏览器自己的动画，两者互相覆盖，表现就是滚动发涩发顿。现在 `.is-lenis` 存在时把 `scroll-behavior` 交回 `auto`，也就是「谁在驱动滚动，谁说了算」。

**镜头关键帧锚在 DOM 元素上，不是锚在滚动比例上。** 每把镜头记录它对应哪个 `[data-anchor]`，以及那一刻该元素的中心应落在视口高度的百分之几。改 CSS 高度不会让镜头和文案错位；反过来，如果两把镜头解析出了倒序，`resolveTimeline` 会在开发模式里警告。

## 让机身像真机

第一版渲染出来被评价为「像模型机」（注塑展示样机）。诊断下来不是模型精度不够，是**材质和光照的分层不够**：一整块均匀哑光的外壳 + 平贴上去的细节。下面每一条都是针对这个的。

**机身不是一个材质，是四个。** 参考图上这三个部位的亮度本来就不同：

| 部位 | 参考图实测 | 处理 |
|---|---|---|
| 正面边框 | `#F7F7F8`　亮度 247　R-B −1 | 盖板玻璃下的白色涂层，漫反射为主 |
| 侧边 | `#F8F8F8`　亮度 248　R-B 0 | 机加工边带，粗糙度 0.26 |
| 背面上段 | `#CBC6C6`　亮度 199　R-B +5 | 喷砂阳极氧化，粗糙度 0.46 |
| 背面下段 | `#A7A2A1`　亮度 163　R-B +6 | 同上，靠环境渐变自然落到这个值 |

最初整机共用 `roughness: 0.30` 一个材质，任何一个面都没有自己的身份，所以读起来就是一块成型外壳。现在几何按 z 切成四区（正面 / 背面 / 直边带 / 两侧倒角），倒角给到近镜面，边缘那道亮线就是从这来的。几何是非索引的，`ExtrudeGeometry` 自带两个 material group，分区用重心 z 判定后重建索引。

**机身基础色是纯白。** metalness 为 1 时材质颜色就是反射率，任何色调都会变成手机上的色调。参考图全身中性偏暖，一点蓝都没有；第一版用了冷色面板和蓝色补光，背面渲出来是 `#CAD2DC`，R-B −18，和参考图的 +5 差了 23 点。

**环境贴图是手绘的 equirect，不是六个盒子。** 金属的质感来自反射到**形状**：一块亮柔光箱紧挨着一块暗遮光板。只有渐变的话，金属看起来就是哑光塑料。2048 × 1024 的画布上按真实产品摄影的布光画了柔光箱、遮光板、地平线光带和一块地面反光板。坐标系：+X 在 u=0.50，+Z 在 u=0.75（正面反射的区域），−Z 在 u=0.25（背面反射的区域，唯一偏暖的地方），画布顶端是正上方。地面反光板是必须的：底面朝下，只能反射正下方，没有它整个底边是黑的。

**正面是一整块盖板玻璃，而玻璃的身份来自它反射出的形状。** 屏幕自己不再有清漆层，改用一层覆盖整个正面的加法混合反射层（黑色 + 加法混合 + 低粗糙度）。普通透明层会把反射和透明度乘在一起，玻璃会既淡又哑。

这一条走过两次弯路，两次都掉进同一个坑：

1. 一开始环境里那块区域是一片平滑渐变，屏幕上只有一条均匀的斜光，眼睛不接受那是玻璃。补了一道亮边紧挨一道暗带之后好了一些，但**边是软的**——`softRect` 的羽化在这份文件里别处是 8 到 40 像素，屏幕倒映出来就是一整片灰色渐变，而那正是磨砂塑料的定义。
2. 后来又反过来把那道带子画得太亮，把屏幕的黑位冲成了浅灰。

现在这个区域的羽化是 1 到 4 像素，因为平面镜的倒影在角度上是 1:1 的：环境里软的边，屏幕上就是软的边。玻璃靠的是亮形状和暗形状之间那道**边界有多锐利**，不是那块形状有多亮。屏幕材质本身的 `envMapIntensity` 也归零了：真屏幕只贡献自己的自发光，任何一点漫反射响应都会把房间光糊回面板上，那是「磨砂」的另一半来源。

**细节是真的挖出来的。** 用 `three-bvh-csg` 在启动时做一次布尔减法，把 USB-C 内腔、十个扬声器通孔、镜头凹腔和闪光灯凹腔从机身上切掉，切完再重新分区并把空腔壁的法线拍平（焊接法线对滚动的倒角是对的，对孔壁是错的，会把表面法线抹进孔里，孔就不像孔了）。两个坑：

- USB-C 的切刀不能用 `CapsuleGeometry`。它的轴就是挤出方向、截面是圆，切出来是个到不了表面的圆孔，还在底边留下 0.75 毫米的皮。
- 判定空腔时体积要**向外**容差。孔壁正好落在切刀表面上，用「向内收缩」的自然读法会把要找的面全部排除；0.76 毫米的扬声器孔缩 0.1 毫米就足以让整个孔壁掉出空腔区，栅格渲染成一片亮点。

**环境光遮蔽用的是 GTAO，只在 `full` 档跑，而且必须给它一个包围盒。** 这个页面的 canvas 是透明的（折页底色在 canvas 下面），背景像素的深度是远平面，GTAO 会把它当成一块很厚的几何体，于是整个机身被判定为全遮挡：半径小的时候整机变黑，半径一大手机直接消失。`setSceneClipBox` 把地平线搜索限制在机身自己的体积内就正常了。另外 `EffectComposer.setSize` 转发给每个 pass 的是 **dpr 缩放后**的尺寸，别再自己用 CSS 尺寸调一次 `setSize`，否则 AO 缓冲尺度不对，会留下铺满表面的接缝。为什么它现在是可选档，见「性能」。

**透明贴片不要写深度。** 背面 logo 是比表面高 0.3 毫米的贴片，写深度的话 AO 预通道会看到一个悬空的矩形板，在它周围压出一圈矩形暗影。

## 降级

- **没有 WebGL**：用 `public/poster.jpg` 加同一套 DOM 文案。海报由 `scratch/poster.cjs` 生成。
- **`prefers-reduced-motion: reduce`**：不创建 Lenis，滚动退回原生，机位完全不动，关掉待机漂移。
- **软件光栅化**（SwiftShader / llvmpipe，常见于无头环境和虚拟机）：把各向异性过滤降到 1、DPR 锁 1，跳过 GTAO 与后处理链。1024 × 6432 的屏幕贴图在软件光栅化下做各向异性过滤会让每帧掉到几秒，而且纹理本身会出现摩尔纹。
- **弱 GPU / 大视口**：走 `fast` 档（无后处理链、无 AO），超出像素预算时再降渲染分辨率。判定与兜底见「性能」。
- **移动端**：`truck` 跟随视口宽高比衰减到 0，并叠加一个按可见高度计算的台座偏移，把机身推离文案所在的那一半。

## 屏幕里的东西

那块屏幕是 1024 × 6355 的 CanvasTexture（设计空间 1440 宽，按真实 iOS 的 pt 尺寸换算绘制：17 pt 正文 = 62 单位，38 pt 通知图标 = 139 单位）。里面是一整屏锁屏加 18 条通知，一次看完不用滚动，这是「超高屏幕」那一段的全部论据。

时钟字号是按屏幕**宽度**定的，不是按高度：参考图里的时钟占屏宽约 44%，按 6:1 屏幕的高度去缩放会把它变成一块广告牌。

**壁纸没有照抄参考图，这是本项目唯一一处刻意偏离参考图的地方。** 参考图里那块屏幕测出来是 `#3C3F42` 到 `#5D6064`，是一块中性灰加一道白色斜光；照着画出来的结果就是磨砂塑料——一块中灰面板配一条柔和白光带，眼睛读到的就是「背光 LCD，而且漏光」，上面盖多少层玻璃都救不回来。真 OLED 是黑的，它显示的一切都是**加在黑色上的光**。所以现在底是 `#04050a`，上面几块很大很软的椭圆色场用 `lighter` 叠上去（深蓝 → 靛 → 紫 → 青），走的是苹果自带深色壁纸的路子。副作用是好的那个：只有面板足够黑，盖板玻璃的倒影才看得见。

色场的 alpha 必须压得很低（0.32 到 0.5）。它们是叠加混合的，0.9 的话面板中间会饱和成浅蓝，又变回一块背光板。

**屏幕是一块自发光面板，不是一个被照亮的表面。** 这是它读起来像不像真机屏幕的分水岭。之前的材质同时挂了 `map` 和 `emissiveMap`（同一张贴图），于是每个像素 = 内容 + 内容再被房间照亮一遍。那个漫反射项会把黑位从 0 抬起来，并把整块面板往环境色上洗——那正是背光 LCD 的样子，也正是 OLED 不是的样子。现在只有 `emissiveMap`，`color` 是黑的，黑位跟着内容走，反射交给上面那层盖板玻璃。

**光晕要烘焙进贴图，不要做后期辉光。** 真屏幕是漏光的：黑底上的白色时钟有一圈可见的光晕，缺了它的渲染屏就是「一张屏幕的照片」。但这个页面的帧预算已经全部花在机身上了，再加一条全屏 bloom 通道不划算，所以光晕直接画进贴图：把面板按 1/4 分辨率复制一份，先 `contrast(2.4)` 再过 `blur()`，最后用 `lighter` 叠回去。顺序很关键——先模糊再叠加会把整块面板抬亮（壁纸亮度直接翻倍，OLED 变成磨砂塑料），先做高通再模糊才只留文字和时钟。默认混合模式下暗部几乎不贡献，所以只有高光真的发光。运行时零成本，代价是启动时多一次模糊。

**盖板玻璃需要环境里有形状可反射。** 正对屏幕看时，反射采样的是环境贴图里 u≈0.75、地平线略往下那一小块（屏幕朝向观众，而摄影机在屏幕上方，所以它的镜面方向是**向下**的）。原来那里是一片平滑渐变，屏幕上只有一条均匀的斜光。现在补了一道亮度贴近面板本身的窄带、边收得很紧：玻璃的身份来自它反射出的**形状**，但那块形状的亮度必须接近屏幕自身的黑，否则黑位被冲掉，OLED 又变回磨砂塑料。

## 性能

这一节在第二轮被整体推翻了，因为第一轮的量测是错的。

**先说量测错在哪。** 无头 Chrome 不保证为页面产帧，而页面内的 rAF 计数器照样按 60 Hz 被调用。于是脚本报出「4K dpr2 满帧 60」，同一台机器上把窗口显示出来再测，同一份代码是 **12.6 fps**。区别只在 `headless: false`。后来所有数字都来自一个真正显示在屏幕上的窗口（`scratch/perf.mjs`），并且固定采样 240 帧而不是固定采样 4 秒——按墙钟结束的话，卡顿帧会提前终止采样，正好把要测的东西漏掉。

**真实的代价全在填充率上。** 在 Intel UHD（ANGLE/D3D11）、2560 × 1217、DPR 1 下逐档拆开：

| 管线 | fps | 中位帧 |
|---|---|---|
| 直接画到默认帧缓冲（驱动 MSAA） | **60** | 16.7 |
| EffectComposer，无 AO，MSAA 4 | 35 | 16.7（夹 283 ms 尖刺） |
| EffectComposer，GTAO，无 MSAA | 27 | 33.3 |
| EffectComposer，GTAO 24 采样，MSAA 4 | **12.6** | 16.7（夹 383 ms 尖刺） |

后三行的中位帧是 16.7 而最差帧是 300 以上，这个形状就是问题本身：它不是「慢」，是**每几帧卡一下**。原因也很具体——GTAO 的预通道是整场景在满分辨率下再走一遍，而 MSAA 4 解析在一个 `HalfFloatType` 目标上是每像素每采样 16 字节：2560 × 1217 下就是两块 100 MB 的缓冲在 composer 里来回乒乓。在统一内存的核显上这就是全部帧预算。

**所以后处理链是一个档位，不是默认值。** `stage.ts` 里有两档：`full`（composer + GTAO + MSAA 4）和 `fast`（直接画到默认帧缓冲，用驱动自己的 MSAA，因为它不离开 tile，几乎免费）。选档先看 GPU 名字和像素量做一次判断，再用真实帧间隔的滑动中位数兜底：连续 30 帧的中位超过 20 ms 就永久降到 `fast`。用中位数而不是平均值，是因为 16.8 的中位配 350 的尖刺，平均值会说这台机器很好。

**最后一道是像素预算。** 4K 视口（830 万 CSS 像素）在核显上无论哪条管线都跑不到 60，这时候降分辨率比卡顿划算：`fast` 档 360 万、`full` 档 830 万像素封顶，超了就按 `sqrt(预算 / 面积)` 缩渲染分辨率，浏览器负责放大。3840 × 2160 因此从 34 fps 回到 57.6，代价是一次 0.65 倍的放大。下限设在 0.5 倍：再低屏幕折页里的通知正文就读不清了，而那一段的全部论据就是「一眼看完」。

修完之后的实测（全部 `headless: false`，固定 240 帧）：

| 视口 | fps | 中位帧 | p95 | 最差 |
|---|---|---|---|---|
| 390×844 dpr3 | 60.0 | 16.7 | 16.9 | 17.0 |
| 1440×900 dpr1 | 60.1 | 16.7 | 16.8 | 21.1 |
| 1920×1080 dpr1 | 60.1 | 16.7 | 16.8 | 17.0 |
| 2560×1217 dpr1 | 60.0 | 16.7 | 16.9 | 17.2 |
| 3840×2160 dpr1（缩到 360 万像素） | 57.6 | 16.7 | 17.0 | 33.4 |

抗锯齿并没有因为砍掉 composer 的 MSAA 而变差：驱动在默认帧缓冲上的多重采样在同样倍率下的边缘质量与 composer 的 MSAA 4 目视无差别，而它是免费的。想亲眼看 `full` 档，加 `?post=1`；其余调试开关是 `?post=0`、`?ao=0`、`?msaa=N`、`?ss=N`、`?dpr=N`，只在 dev 下生效。

**上面那张表是在一台空闲的机器上量的，而同一台机器在忙的时候会在 2560 × 1217 上掉到 45 fps 左右**（中位帧仍是 16.7，掉的是 p95）。所以光靠静态预算不够，还有一道自适应：每 30 帧统计一次「比本机刷新周期明显长的帧」有几帧，是分布尾部而不是中位数或均值——16.7 的中位配 50 的 p95，均值和延中位数都会说这台机器很健康。判据第一条是把后处理链降到 `fast`，之后每次把像素预算乘 0.7，最低 180 万像素。只降不升，所以桌面上别的东西忙一下不会让画面来回抖。

**另外两处仍然成立的修复**（第一轮就做完了）：滚动中 2733 毫秒的单帧，来自 three 在材质第一次被真正绘制时才编译着色器，而折页 5、6 的材质在摄影机走到那里之前一直被视锥剔除——`renderer.compile(scene, camera)` 在启动时把整个场景的程序编译掉（用 `traverseVisible`，不受视锥影响），最差帧降到 16.8 毫秒。启动时约 700 毫秒的空白拆成两段：先画文案（`is-ready`），让浏览器出一帧，再建三维模型（`is-3d`，画布淡入），文案可见时间 700 → 105 毫秒。

性能分段埋点用 `performance.mark`/`measure`，名字是 `dsh:*`。

## 已知的取舍

- **参考图自身不一致。** 图上印着 432 × 72 × 7.8 毫米，但画出来的比例约为 4.26:1，也就是 432 × 101 × 12.7 毫米。432 = 6 × 72 是刻意凑的整数，整页的「长到装不下」也依赖 6:1，所以取标注尺寸为准，把图里所有**脸部比例**（内缩宽度、镜头位置、logo 高度、天线带、按键、接口）按占机身的比例换算过来。
- **屏幕四角是 7 毫米圆角，不是直角。** 量参考图时，屏幕在第一个暗像素行就占满整宽，看不出圆角，所以一开始只留了 2 毫米。渲染出来那个尖角是整块屏幕上最假的一处：真机屏幕的角半径跟着盖板玻璃走，2 毫米的角在近景里像一个贴错位置的矩形。
- **构建产物偏大，基本都是 three.js。** 这个页面不需要首屏之外的内容，真要进一步压可以按折页做动态导入。
- **镜片和闪光灯是一个凸面圆顶加一个凹腔，不是真正的镜组。** 真机镜头是好几片玻璃加镀膜，这里用 `iridescence` 伪造了镀膜那层紫绿色反光。凑近到 50 毫米以内会看出来。
- **没有分模线。** 玻璃与侧边之间那道深色细缝、SIM 卡托的分割线都还没做，表面是完美连续的，这一点仍然偏 CG。
- **没有微表面粗糙度贴图。** 喷砂铝在掠射角下应该有一层细颗粒打碎反射，现在是数学上完美的表面。
- **弱 GPU 上没有 AO。** `fast` 档为了帧率把 GTAO 整个砍掉了，凹腔的立体感只剩下空腔壁自己的暗材质在撑。实测下来代价主要出现在镜头凹腔这类浅凹处，接口和扬声器孔因为本身就深，看不出来。
- **`full` 档在核显上仍有极淡的 GTAO 过渡带。** 半径给大会整机消失，给小的代价就是过渡略软。它还会给平面压掉几个百分点的亮度，正面边框因此停在 225，参考图是 247。
- **正面边框亮度差 22。** 参考图的边框在盖板玻璃下几乎纸白（亮度 247），现在渲染到 225。原因是漫反射辐照度受环境平均值限制，继续加 `envMapIntensity` 收效很小，而调曝光会让背面和壁纸过冲。要彻底对齐需要重画环境的亮度分布，不是调一个数的事。

## 量测脚本

`scratch/` 里这几个是这一轮真正用到的，都要求 `headless: false`：

| 脚本 | 用途 |
|---|---|
| `perf.mjs` | 帧时间分档实测，`PERF_RUNS='base,ao=0,msaa=0'` 这样传 |
| `shoot.cjs` | 逐折页截图（2560 × 1217 那一套是 `SHOOT_W/H` 传的） |
| `one.mjs` | 单折页截图 + 读回摄影机位置，排查构图问题用 |
| `crop.mjs` | 裁一块放大看锯齿 |
| `sample.mjs` | 把截图打成粗亮度图 + 列均值，用来找「画面里到底有没有手机」 |

三个坑：窗口必须在屏幕上（无头 Chrome 不保证产帧，页面内 rAF 计数器照样照 60 Hz 被调用，第一版量测就是这么错的）；`page.screenshot()` 里的 canvas 只有在 `requestAnimationFrame` 真的跑过之后才有内容，隐藏标签页截出来是一张白纸；`scroll-behavior: smooth` 会让 `window.scrollTo` 变得不确定，必须传 `behavior: 'instant'`。
